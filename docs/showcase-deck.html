01 · Problem

OBJ-01OBJ-02OBJ-03

Source: docs/problem_statement.md, approved 2025-01-16.

Triage is four manual lookups before anyone touches the fix

When production breaks, an on-call engineer reads the alert, then goes hunting: the log platform, the deploy history, the commit that landed an hour ago, and the memory of whoever handled it last time. The diagnosis is slow, and it is different every time depending on who is holding the pager.

What the manual loop costs

  • Time — investigation happens before remediation, so every minute of it is downtime.
  • Consistency — two engineers given the same alert produce different diagnoses and different fixes.
  • Knowledge loss — last quarter's identical incident was resolved, written up, and then never consulted again.

The volume it happens at

Alerts100–500per day, 1,000+ in a major incident
Application logs10–100 GBper day, per tenant
Config changes10–100per day, across VCS and deploys
Runbooks50–100per week, 200+ in an outage window

03 · Users

FR-08FR-10NFR-04

Roles map 1:1 onto Cognito groups in template.yaml.

Three roles, deliberately unequal

Every user belongs to exactly one tenant and holds exactly one role. The split is not cosmetic: it is what makes the approval gate meaningful, because exactly one role can authorise a change to live infrastructure.

Cognito group

TenantAdmin

The first person to sign up from an email domain. Sees everything, manages the team and integrations, and is the only role that can approve remediation.

  • 5–50 concurrent per tenant
  • Cannot be demoted if last remaining admin

Cognito group

TenantEngineer

Everyone who signs up afterwards. Works incidents: reads diagnoses and runbooks, raises incidents by hand, and cannot approve.

  • 5–50 concurrent per tenant
  • Promoted to admin only by an admin

Cognito group

TenantLeadership

Accountable, not operating. Gets the cross-incident overview, the audit trail and the team list — and deliberately cannot raise or approve anything.

  • 2–10 concurrent per tenant
  • Assigned by an admin

Scale the design is sized for

Concurrent diagnostic sessions2–5baseline; 10–20 during multi-tenant incidents
Alert volume growth+50%over 12 months, without re-architecture

Why tenancy is not a signup field

The BRD expects OAuth/SAML per tenant. With self-signup, a writable custom:tenant_id would let anyone claim an existing tenant's id and read its incidents — and every control below that point would faithfully scope access to whatever the token claimed. So tenancy is derived server-side, once, from the verified email domain.

06 · Boundaries

C-01 → C-05Out of scope

C-03 is the constraint that shapes the product most.

Constraints that shaped the design — and what was left out

Constraints

C-01Zero cross-tenant visibility. Pooled storage is allowed; leakage is not. Answered by defence in depth rather than one check.
C-02Config data may be unavailable. A diagnosis missing change history must say so rather than imply confidence it has not earned.
C-03Remediation is a recommendation. Human approval is required before anything executes. This is the reason the approval gate exists at all.
C-04Correlation needs timestamp and service alignment across systems that do not agree on either.
C-05Log query speed is the customer's. Their platform's latency and retention bound NFR-05, not ours.

Explicitly out of scope

  • Infrastructure provisioning or deployment orchestration
  • Predictive outage prevention and anomaly detection
  • Automatic remediation with no human approval — excluded by C-03, not by effort
  • Integrations beyond the five named systems
  • SLA management, on-call scheduling, escalation workflow
  • Executive dashboards and post-incident trend analytics
  • Per-tenant custom runbook templates — standardised only

The consequence of C-03

Arcadia is not an auto-remediation system, and is not trying to be. It compresses the diagnosis, then stops at a gate that exactly one human role can open. Everything downstream of that gate — the platform call, the IMS update, the audit record — exists to make opening it safe and reviewable.

09 · Orchestration

Req 2.1–2.3NFR-01

diagnosis_pipeline.asl.json — 10 states, one Parallel, one Fail.

What happens when a stage fails

Every stage retries with exponential backoff, then routes to a single failure path that marks the alert, preserves the whole execution state, and tells ops which identifiers to look at. Silence is never an outcome.

States

StateTypeTimeoutOn error
CorrelateContextParallel65 sCatch → MarkAlertFailed
MergeCorrelationPass——

GenerateRcaTask45 sRetry ×2, then Catch

The failure path

The case a Catch cannot handle

An execution killed by the state machine's own 300-second timeout runs no Catch at all — so TIMED_OUT and ABORTED executions are picked up by a separate EventBridge rule and marked failed from outside the execution. Without it, an SLA breach would leave an alert sitting in processing forever, which reads as "still working" rather than "gave up".

Progress reporting

Each task marks its own stage on the alert row as its first action, so the console can draw a live timeline. It is advisory by design: a failure to record progress must never fail the stage that is reporting it.

10 · Ingestion

FR-01NFR-02Req 1.1–1.3

Two ways in, two different trust models.

Two front doors, and why they trust different things

Public webhook

POST /v1/alerts · ingestion API

  • API key on a usage plan gates the endpoint.
  • HMAC over the raw request body, signed with that tenant's secret from Parameter Store.
  • Only after both pass is the tenant_id inside the payload trusted.
  • A signature failure writes nothing to the Alerts table.
  • Duplicate alert_id is dropped by a conditional write, not by a read-then-write race.
  • Returns 202 once stored and dispatched.

Authenticated console

POST /v1/alerts · admin API

  • Takes the tenant from the authorizer context and ignores any tenant_id in the body — otherwise a signed-in user of one tenant could write an incident into another.
  • Requires the create_incident capability, so leadership cannot raise one.
  • Records source: console so the overview can tell hand-raised incidents from machine ones.
  • Everything after validation is shared with the webhook through one module, so both produce the same row and start the same pipeline.

Store, then dispatch — and mean it

The alert row is written before the EventBridge dispatch. If the write succeeds and the dispatch does not, the request is answered with a 5xx rather than acknowledged, and the sender's retry re-dispatches the stored alert instead of creating a second one. Acknowledging a stored-but-undispatched alert is the failure mode that looks fine from the outside and never produces a runbook — an UndispatchedAlertsAlarm watches for it as well.

11 · The AI layer

FR-04FR-05FR-06Req 4.1–4.3

Grounding is the difference between a plausible answer and a usable one.

The model never sees the alert alone

A language model handed only "checkout-api 5xx rate above threshold" can write a confident, generic, useless paragraph. Three retrieval steps run first, and the diagnosis is prompted with all of them.

Step 1 · correlate

The tenant's log platform and VCS/deploy history are queried with the tenant's own credentials, in parallel, and cached to S3 under the tenant prefix.

Step 2 · embed

Alert + logs + config are embedded with cohere.embed-multilingual-v3, invoked with its bare model id directly in ap-southeast-1.

Step 3 · retrieve

That vector queries the tenant's own namespace in the S3 Vectors index, returning similar past incidents and how they were actually resolved.

Step 4 · generate

Claude Haiku 4.5 is prompted with alert, correlated signals and retrieved neighbours, and returns a root-cause summary plus prioritised steps.

Models, exactly as invoked

Model idUsed for
global.anthropic.claude-haiku-4-5-20251001-v1:0RCA, remediation plan, runbook drafting
cohere.embed-multilingual-v3Embeddings for retrieval

The global. inference-profile prefix on Haiku is not decoration — a bare model id fails at runtime with "on-demand throughput isn't supported", inside the deployed application where it is hardest to diagnose. Cohere is the one local model and takes no prefix.

Output shape, not free text

The RCA call returns a one-sentence cause, reasoning, a confidence value, a model version, and remediation steps as P1/P2/P3 objects each with text and an optional command. The console renders that structure; it does not parse prose.

C-02, surfaced rather than hidden

Config history is optional — some tenants have no VCS integration. A diagnosis produced without it is marked as partial-evidence and its confidence is downgraded, because a diagnosis that silently omits change history implies confidence it has not earned.

13 · Tenant isolation

FR-08NFR-07C-01Req 9

Storage is pooled. Isolation therefore has to be earned four times over.

Four independent layers, so one bug is not a breach

Tenants share tables and buckets, which is what makes the economics work — and means application code is the wrong place to put the only check. Each layer below holds on its own if the layer above it is wrong.

LayerMechanismWhat it stops
1 · Data model Every DynamoDB table is partitioned by tenant_id; every S3 object lives under tenant/{tenant_id}/ A query written without a tenant filter has nowhere to land — there is no table-wide read path in the handlers.
2 · IAM Every data-plane call runs under a short-lived sts:AssumeRole session tagged with the caller's tenant. The role's policy pins dynamodb:LeadingKeys and the S3 prefix to ${aws:PrincipalTag/tenant_id} A bug in application code. The credentials physically cannot touch another tenant's rows or objects, whatever the code asks for.
3 · Application encryption RCA summaries, remediation steps and retrieved-incident references are Fernet-encrypted with a per-tenant DEK before they are written A misrouted row. Pooled storage never holds another tenant's readable plaintext, even in the wrong partition.
4 · Identity The authorizer verifies the ID token's RS256 signature against the pool's JWKS and checks issuer, audience, token_use and expiry before reading custom:tenant_id A token minted by a different Cognito user pool being trusted for the tenant it claims.

Also scoped per tenant

  • The S3 Vectors namespace — RAG can only retrieve this tenant's own past incidents
  • The ingest HMAC secret, the DEK and every integration credential, under /{prefix}/tenant/{tenant_id}/
  • The stack's IAM roles trust only ${NamePrefix}-* principals, so deploys are isolated from each other's roles as well as their data

The permission that is easy to miss

Passing session tags needs sts:TagSession as well as sts:AssumeRole — in the caller's policy and in the role's trust policy. Granting only AssumeRole makes every data call fail with AccessDenied, which looks like a broken application rather than a missing permission.

14 · Tenancy

FR-08Req 9.1

Decided server-side, exactly once, by a Cognito trigger.

How a new user acquires a tenant

Two Cognito triggers do all of it. Nothing in the sign-up form can name a tenant or ask for a role, because both are decisions the client is not allowed to make.

PreSignUp · fn-pre-signup

  • A work email is required. Consumer domains are refused, because tenancy is derived from the domain and a consumer address cannot belong to an organisation. The form checks the same list client-side so the refusal appears before submitting.
  • Auto-confirms the account, so signing up is one step with no emailed code.

PostConfirmation · fn-tenant-provision

  • Derives custom:tenant_id from the verified email domain and writes it to the user.
  • Creates the tenant's DynamoDB row and its key material: DEK, ingest HMAC secret.
  • The first user of a domain becomes its TenantAdmin; everyone after joins as TenantEngineer.
  • Runs exactly once per user, ever.

Two guards worth naming

Cognito's admin APIs are account-wide, not tenant-scoped, so fn-team adds what Cognito does not:

  • A role change looks the target up in the caller's own tenant first and refuses if the row is not there — without it, an admin of one tenant could promote a user in another.
  • The last remaining admin cannot be demoted. Only the first user is ever made admin automatically, so a tenant that demoted its only one could never approve remediation again.

Known consequence, chosen knowingly

Because sign-up auto-confirms, the email address is never verified. Anyone can sign up as someone@bigcorp.com and land inside BigCorp's tenant. Deleting the PreSignUp trigger restores the verification step and nothing else has to change — provisioning runs on confirmation either way. Acceptable for a prototype; stated rather than left implicit.

One capability matrix, checked twice

Three handlers each used to carry their own group check. Three copies of one idea drift apart quietly, and the user discovers the disagreement as a 403 on a button that looked enabled. There is now one matrix, and a test that fails if the server's copy and the console's copy disagree.

Server — authorisation

Every capability is checked inside the handler, from the role the authorizer read out of a cryptographically verified ID token. Anything the browser decides, the browser can skip with the developer tools open.

Console — presentation only

The mirror decides which controls render, and which render disabled with an explanation naming who can. A non-admin should see why they cannot approve, not discover it through a 403. The 403 stays implemented as the fallback for a token whose group changed between page load and click.

16 · The gate

FR-09C-03Req 7.1–7.3Req 8

The one surface where a UI mistake causes real damage.

Approval is a decision, not a button

Approving runs real changes on live infrastructure. Four things therefore happen around the click, and each of them exists because of a specific way this can go wrong.

What the operator sees

  • A warning stating plainly that this executes real changes on live infrastructure.
  • The exact normalised actions, their target system and their blast radius — before any button, including when an action is irreversible.
  • A checkbox — "I have reviewed this runbook and accept the blast radius" — that the primary button stays disabled until.
  • For non-admins, Approve is disabled with the reason and who can approve.
  • Typed text never approves anything. "approve it", "run it", "ship it" all resolve to focusing the checkbox, and the assistant says plainly it will not approve on the user's behalf.

What the backend does

  1. Check the capability against rbac.py; a non-admin gets 403 and the platform is never called.
  2. Claim the approval with a conditional write before the outbound call, so a double-click or a client retry cannot execute the remediation twice.
  3. Write the audit record before and after the platform call — including refused attempts, with actor, timestamp, action, target and result.
  4. Notify the IMS asynchronously. A failure there is logged and never blocks the remediation flow.

Declining is a decision too

There is a real POST /v1/runbooks/{id}/decline. A decline is recorded and audited, not a UI-only state that vanishes on reload — "we looked and chose not to" is exactly the kind of thing an incident review needs to see.

Incident detail

The live timeline

A five-minute wait cannot be a spinner. Six named stages with glyph and state, an elapsed clock, and a budget bar against the 300-second SLA.

The SLA figure is real

The overview's SLA number is the actual NFR-01 measurement: time from alert arriving to runbook ready, against the five-minute budget. An incident with no runbook counts as pending inside the budget and breached once past it — so a pipeline that silently stopped shows up, rather than being omitted for having nothing to measure.

How it is built

  • One HTML file. The shared logic in lib/triage.mjs is inlined into it, and the deploy fails if the inlined copy has drifted.
  • Colour, type and spacing come from design/reference.html; a test compares the two token sets so they cannot silently diverge.
  • Tokens in sessionStorage, so a bearer token does not outlive the tab that obtained it.
  • Severity is never colour-only — every state pairs a glyph and a word with its tone.

18 · Integrations

FR-02FR-03FR-11Req 8

Tenant-supplied URLs are attacker-controlled input to a function holding credentials.

Four outbound integrations, one guard

Tenants configure their own log platform, VCS, remediation platform and incident management system through the API. Those URLs then reach a Lambda that holds that tenant's credentials — which makes every one of them untrusted input.

Configured by the tenant admin

IntegrationDirectionUsed at
Log aggregationPullCorrelation stage
VCS / deploysPullCorrelation stage
Remediation platformPushAfter approval
Incident managementPushAfter execution, async

GET / PUT / DELETE /v1/integrations, restricted to TenantAdmin and audited. API keys are write-only: a read returns the endpoint and a boolean for whether a key is set — never the key.

The guard, in two halves

Every outbound call goes through one module: https only, the resolved address must be public, redirects are refused, the response is size-capped.

  • assert_target_shape judges what a URL shows on its own — scheme, and a literal IP. This is what the settings API validates a stored endpoint against.
  • The full check adds resolution and runs on every call — because a hostname that resolves publicly at write time can be repointed afterwards.

The window that remains

The guard resolves a hostname and checks the address, then the HTTP client resolves again. A DNS record that changes in between is not caught. Closing it means pinning the checked address and carrying the hostname for TLS verification by hand — acceptable at prototype scale, and documented rather than left implicit.

21 · Trade-offs

Prototype scope

Every one of these is written down in the repository, not discovered later.

Six things we chose, knowing the cost

A prototype that hides its compromises is worse than one that names them. These are decisions, with the reason and the consequence stated.

01 · Key material in Parameter Store, as String

The deploy permissions boundary grants Secrets Manager read only — no CreateSecret — so a PostConfirmation trigger could never create a tenant's DEK. The same boundary grants no kms:*, ruling out SecureString. Cost: anyone holding ssm:GetParameter on that path reads plaintext. One module talks to the store, so moving later is one file plus IAM.

02 · Sign-up does not verify the email

One-step signup, no emailed code. Cost: anyone can claim a domain's tenant. Deleting one trigger restores verification and nothing else changes.

03 · Runbook documents are not DEK-encrypted

The RCA text is; the 1–3 MB runbook restating it is SSE-S3 only, because it is delivered as a presigned GET and an application-layer key makes that impossible. Boundary: the tenant-prefixed IAM condition plus a fully blocked bucket.

04 · Client-side RBAC is presentation only

The console's matrix decides what renders and what renders disabled. It is not authorisation — every capability is re-checked server-side, and a parity test keeps the two copies honest.

05 · The console is not the chat interface

The design spec describes a chat-first console around a /v1/chat endpoint that does not exist. The deployed console implements the parts that run on endpoints that do; the chat prototype stays in the repo as the offline design reference and is not deployed.

06 · A pathological retry path can breach the SLA

Per-attempt timeouts are sized for the expected 195 s path. If every stage retries, the execution hits the 300 s ceiling — which is the intended behaviour for an SLA guard, and is now both alarmed and recorded on the alert row rather than silent.

And two resources deliberately idle

The audit-exports bucket awaits the compliance-export path; the runbook-ready topic is published to but has no subscriber — a subscription is all a notification channel needs. Both are named in the stack outputs.

Where it stands today

All eleven functional requirements are implemented and deployed as one SAM stack in ap-southeast-1. An alert posted to the webhook is normalised, correlated, RAG-grounded, diagnosed by Claude Haiku 4.5 and rendered as an approvable runbook inside a five-minute budget that the state machine enforces rather than merely measures — and no step of it can read another tenant's data.

The one claim worth repeating

Arcadia does not remediate. It compresses the four manual lookups on slide 2 into 195 seconds of machine work, and then stops at a gate that exactly one human role can open — with the blast radius named before the button, and the decision recorded either way.

Arcadia — the keystone is the root cause.
